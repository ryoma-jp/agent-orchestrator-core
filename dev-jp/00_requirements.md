# マルチタスク型AIエージェント基盤 要求仕様書

## 1. システム概要

本システムは、ユーザーからの多様な指示（調査、コーディング、アイデアの壁打ち等）を単一のフロントエンドUIで受け付け、OpenAIのBYOK（Bring Your Own Key）基盤上で稼働するGPT-6系高性能モデル（管理エージェント）**と、動的に生成・並行実行される**軽量モデル群（サブエージェント）が連携して各種タスクを効率的に並行実行・完遂するためのバックエンド基盤およびUI環境である。

---

## 2. システムアーキテクチャ概要

```
[フロントエンドUI (タスク管理・複数並行指示)]
       │
       ▼ (API / WebSocket / SSE)
[管理エージェント (高性能モデル: GPT-6-Sol 等)] ── OpenAI API (BYOK)
       ├─► ユーザー意図の解釈・高度なタスク分解・計画立案
       ├─► サブエージェントの動的定義・生成・統括
       ├─► スキルの動的取捨選択と指示
       │
       ├─► [サブエージェント群 (軽量モデル: GPT-6-Luna 等)] ── OpenAI API (BYOK)
       │      └─► 非同期並行実行・単一タスク完遂
       │
       ├── (動的マウント / プラグイン読み込み)
       │      │
       ├─► [スキル基盤 (OpenAI Tool Calling 互換)] ─── [ Private Skills Directory ]
       └─► [知識データベース (RAG / 外部参照)] ─────── [ Private Vector DB Storage ]

```

## 3. 詳細仕様：① エージェント層（GPT-6系 & BYOK準拠）

### 3.1 認証・APIキー管理（BYOKアーキテクチャ）

* **一元化されたAPIキー利用**: システム全体でユーザー指定のOpenAI API Key（環境変数 `OPENAI_API_KEY` またはセキュアなキー管理ストレージ経由）を利用。
* **モデル柔軟性**: API経由で提供される最新のGPT-6系フラグシップモデルおよび高コストパフォーマンスな軽量モデルを、管理・サブエージェントそれぞれに自由に配置可能。
* **レートリミット（TPM/RPM）制御**:
* 複数サブエージェントの並行実行時に発生する `429 Too Many Requests` を回避するため、バックエンド側で**指数バックオフ付き自動リトライ機能**および**同時並行数のスロットリング制御**を実装。



### 3.2 管理エージェント（オーケストレーター）

* **採用モデル**: GPT-6系高性能モデル（例: **GPT-6-Sol** 等）
* **インターフェース**: OpenAI API / Agent SDK (Python/TypeScript) による非同期API呼び出し
* **主要機能**:
1. **高度な意図解釈・タスク分解**: ユーザーの曖昧または複雑な指示の意図を正確に捉え、依存関係のあるサブタスク群へ細分化。
2. **サブエージェントの動的生成**: サブタスクの性質に応じたシステムプロンプト、必要最小限のスキルセット、適切なパラメータ（Temperature等）を動的に構築し、サブエージェント（GPT-6-Luna等）をインスタンス化。
3. **成果物の統合・品質管理**: サブエージェント群からの出力を統合・検証し、品質基準に満たない場合は自動修正指示（リトライ）を発行。



### 3.3 サブエージェント群（ワーカー）

* **採用モデル**: GPT-6系軽量モデル（例: **GPT-6-Luna** 等のコスト効率に優れたモデル）
* **実行形態**:
* バックエンド側で非同期タスク（`asyncio` やタスクキュー）として独立したスレッド／コンテキストで動的実行。
* ターミナル操作やコード実行を伴う場合、サンドボックス環境上で安全に動作する軽量CLIラッパーと連携。


* **プロンプト & ツール最適化**:
* 軽量モデルのTool Calling精度を最大化するため、サブエージェント1体あたりに付与するスキル（Tool）は**1〜2個に厳選**し、文脈をクリーンに保つ。



### 3.4 エージェント間通信・フォーマット

* **OpenAI Tool Calling (Function Calling) 準拠**:
* スキル呼出やサブエージェントへの指示はすべて最新のOpenAI標準 `tools` パラメータ（JSON Schema）に準拠。


* **構造化出力（Structured Outputs）**:
* サブエージェントから管理エージェントへのレスポンスは、パースエラーを防ぐため `response_format: { type: "json_schema" }` を活用し、厳密に型定義されたJSONでやり取り。

## 4. 詳細仕様：② ノウハウの管理とリポジトリ分離アーキテクチャ

### 4.1 基本方針（Public / Private の切り分け）

* **GitHub Public Repository（エージェント基盤コア）**:
* 管理・サブエージェントの制御ロジック、タスク管理UI、通信レイヤー、APIルーティングなど、汎用的なプラットフォーム機能のみを公開領域で管理。


* **Private Storage / Git（独自のノウハウ）**:
* 競合優位性の源泉となる「独自開発のカスタムスキルコード」および「蓄積されたナレッジデータベース（RAG）」は、完全な非公開領域として分離管理。



### 4.2 プラグイン（Extension）構成

基盤コア側が特定のノウハウに直結しないよう、**依存性注入（Dependency Injection）**および**動的ロード機構**を採用。

```
[GitHub Public Repository (基盤コア)]
  ├── /core         (オーケストレーション & タスク制御エンジン)
  ├── /ui           (マルチタスク表示フロントエンド)
  └── /interfaces   (スキル・RAGの抽象インターフェース定義)
         │
         │ (実行時に動的マウント)
         ▼
[Local / Private Storage (ユーザーノウハウ)]
  ├── /skills       (独自スキルモジュール - Private Git またはローカルパス)
  └── /knowledge_db (独自ベクトルデータベースストレージ - .gitignore 対象)

```

1. **インターフェースの抽象化**: 基盤コアには「スキル呼び出し規約（JSON Schema）」と「検索インターフェース」のみを定義し、具体的な処理内容は記述しない。
2. **動的ロード**: 起動時またはタスク実行時、設定で指定されたプライベートディレクトリ（例: `~/.ai_agent_base/private_skills/`）からPythonモジュール等を動的に読み込んで使用。
3. **知識DB（RAG）の完全分離**: Vector DBのストレージ実体（Chroma/Qdrant等のボリューム）および元ドキュメントをPublic管理外に隔離。

## 5. UIおよびフロントエンド要件

* **複数タスク並行管理ダッシュボード**: 調査、コーディング、アイデア出しなど、並行して走る複数の指示を別々のカード／タブとして視覚的に管理。
* **リアルタイムログ・進捗表示**: WebSocketまたはServer-Sent Events (SSE) を用い、管理・サブエージェントの思考プロセス、Tool Calling実行履歴、中間成果物をリアルタイムにストリーミング表示。
* **Human-in-the-Loop 割り込みUI**: 破壊的処理（ファイル書き換え、外部API実行等）の前にユーザー確認用の「承認／却下」ダイアログを自動ポップアップ表示。

---

## 6. 安全性・品質管理・追加要件

1. **自己修復（Self-Correction）**:
* サブエージェントがTool Callingのフォーマット崩れや実行エラーを起こした場合、エラー内容をプロンプトにフィードバックして最大3回まで自動リトライ。


2. **安全制御（ガードレール）**:
* シェルコマンドやファイル操作スキルはサンドボックス環境で実行を強制し、権限昇格や不正アクセスをガード。


3. **コンテキスト・ウィンドウ自動削減**:
* タスク実行が長期化した際、ログや過去の対話履歴を背景で自動要約・プルーニングし、トークン費用肥大化とコンテキスト溢れを防止。


4. **ステートの永続化**:
* ネットワーク切断や基盤再起動時にもタスクを再開できるよう、タスクの進捗ステートを軽量DB（SQLite等）へ随時保存。
